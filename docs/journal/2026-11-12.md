## SIGXCPU

- **2.52.6 cannot be configured out of its SIGXCPU handler.** `RealTimeThreads`' constructor installs it unconditionally; `setEnabled(false)` only stops promotion. The UI process constructs `RealTimeThreads` with every web/network process connection: `AuxiliaryProcessProxy::didFinishLaunching` hard-codes a `UserInteractive` receive queue, which maps to `SCHED_RR`. There is no setting, environment variable or public API. Evidence: `experiments/webkitgtk-spike/evidence/linux/integration-feasibility/sigxcpu/`.
- **WebKitGTK 2.54.1 removed `RealTimeThreads`** (cherry-pick of 319617@main, bug 319535): nice levels through RealtimeKit plus `sched_setattr` utilization floors, no `sigaction`. 2.54.0 still installs the handler, so the minimum is 2.54.1, not 2.54.0. With Debian's 2.54.2 binaries (mixed-package diagnostic), the VM-free host kept Go's SIGXCPU handler through open, second window, inspector, close and reopen, and a Go subscriber received 10 of 10. The control received 0 of 10. Proposal to Michael: require ≥ 2.54.1 via the public version functions, plus an optional detection-only disposition audit. Nothing was patched.
- RealtimeKit answers "Access denied" to processes started from this harness, which runs in a systemd user-service scope. So no `SCHED_RR` thread or nice change was ever observed, and the demotion callback ran with nothing to demote. Don't read the absence of real-time threads here as WebKit's behaviour in a granted session.
- `vmwatch_gdb.py` now has optional, version-specific watches. Its resolution check exempts them, so a missing `RealTimeThreads` on 2.54 is not a monitor failure. Libc's `sched_setscheduler` has no debug types, so returns are read from `%rax`.

Still pending: a supported 2.54.x runtime, the old driver cases affected by recent changes, Michael's manual error-page check, the private-symbol and Linux-readiness decisions, and Windows. ## Cgo comparison: result

- **cgo does not change JSC/WebKit signal coexistence.** WTF and WebKit take signals with `sigaction` from inside their own initialization. cgo and purego's `fakecgo` run Go identically: `iscgo`, signal-blocked `pthread_create`, `asmcgocall`, `cgocallback`, C-visible `setenv`. Dispositions, delivery and stray outcomes matched in both hosts on 2.52.6. Evidence and the decision proposal: `experiments/webkitgtk-cgo-spike/README.md`. Browser policy, lifecycle and packaging validation were not started, per the brief's stop condition.
- **New hazard found (both bindings, VM-free host):** after WebKit initializes, any signal on JSC's GC signal (SIGUSR1 unmodified, or the reserved one) kills the process. `signalHandlerSuspendResume` dereferences a null `targetThread` (`ThreadingPOSIX.cpp:124`), because nothing ever suspends in a VM-free host. Moving the GC signal moves the hazard; it does not remove it.
- `JSC_SIGNAL_FOR_GC`, set by the host through `os.Setenv` before the first WebKit type, reserves the GC signal without the private symbol. It works with both bindings. JSC logs "invalid option" once per inheriting process, and every child process inherits the variable.
- The proposal awaiting Michael:
  - **GC signal:** either a never-send restriction on a reserved signal, or restoring Go's handler after WebKit's synchronous, once-only install. The second is dead code in a VM-free host, and an illegal host VM would then hang on its first GC rather than corrupt memory.
  - **SIGXCPU on 2.52.x:** an application restriction plus a disposition audit.

  Nothing is implemented.
- With cgo, the Go runtime installs its own handlers through libc (`x_cgo_sigaction`), so libc `sigaction` watches are no longer native-only; `probe.py` separates them. A cgo-linked WebKit is mapped before `main`, so native-only executables importing it fail to start without WebKit installed. Root suite unchanged and passing with `CGO_ENABLED=0`. Nothing committed.

## Windows feasibility: passes B–D

Implemented and run on the Windows host at `f71c306` plus the uncommitted tree; record in `experiments/webview2-spike/evidence/windows/integration-feasibility/results.md`, raw run in `run/`. 19 of 22 scenarios pass; the three failures are findings, left failing on purpose. Nothing committed.

- **WebView2's navigation cancellation is not a network boundary.** `NavigationStarting`/`FrameNavigationStarting` with `Cancel` keep the window on its page, but a GET navigation's request still leaves, with the credential cookie (form POST navigations were not sent). Native interception (`AddWebResourceRequestedFilter("*", ALL)`, answer anything off-origin) is the boundary; don't describe navigation policy as preventing the request on Windows.
- **WebSocket handshakes are invisible to `WebResourceRequested`.** Under interception alone one reached another port with the credential; the guard's CSP `connect-src 'self'` stopped it. On Windows CSP is load-bearing, not a second line.
- **Chromium's transport re-sends a request whose connection closed with no response, POST included.** One 307-preserved POST navigation reached the server twice over two connections 1 ms apart with no host or page action; failed GETs arrive 2–3 times per navigation (as Linux saw). The host cannot prevent it; "no replay by Retry" is not "at most one delivery". Judge Retry by navigations, never by server counts.
- `NavigateToString` navigates to a `data:text/html;base64,…` URI (opaque origin): the policy must admit exactly that navigation while the host's error page is pending, or the window stays blank. After a redirect, a failed navigation's `HttpStatusCode` is the redirect's with `IsSuccess` false; judge "the server answered" by `WebResourceResponseReceived` for the document request. When nothing replaced a failed page, WebView2 reloaded it by itself about a second later (kept in `run/development/`); always replace a failure promptly.
- `Controller.Close` releases a still-pending completion handler (GetCookies) without invoking it: release accounting must treat a freed handler as settled (`completion-dropped`), not wait for a call that never comes. `BrowserProcessExited` fires 255–295 ms after `Close` in every case but one (6.56 s); delete the profile only after it, then one `RemoveAll` attempt sufficed every time.
- `AddOrUpdateCookie` is synchronous with no completion; `GetCookies` afterwards lists the cookie before navigation, and the guard saw no cookie-less first request. WebView2 also fetches `/favicon.ico` from an owned origin (admitted, 404). `ICoreWebView2_13` is vtable slot 105: the `com` type's array bound is now 192.
