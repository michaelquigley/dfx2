# 2026-11-02

## Windows native spike (branch `spike/windows-native`)

The Windows host session implemented both stages of
`docs/future/windows-native-spike.md` in `experiments/text-spike`. The
results, the audition table and the evidence are in `docs/future/text.md`,
"Windows results". Nothing is committed: it's in the working tree for
Michael.

- **Don't move the Windows frame back into the Go heap.** On Windows, Go
  reserves its heap in 4 MB arenas, each its own `VirtualAlloc`.
  `SetDIBitsToDevice` silently set 0 lines, with `GetLastError` 0, exactly
  when the frame straddled an arena boundary. `window.pixels` gives the
  frame one `VirtualAlloc` instead. That much was observed. That GDI rejects
  buffers spanning allocations is the inferred mechanism, not a documented
  one. Expect the same with any OS API handed a large Go buffer. dfx2's
  surfaces should own native memory.
- **Coupling:** `window.pixels` relies on `text.Frame.Resize` reusing
  `Pix` whenever `cap(Pix)` suffices. If `Resize` ever reallocates
  unconditionally, the Windows frame silently returns to the Go heap, and
  the intermittent black windows return.
- **The host is a QEMU VM over RDP** (one 3440×1440 Remote Display Adapter
  display at 96 dpi). The `WM_DPICHANGED` path has never run, and the text
  judgments are of RDP-delivered pixels. Rerun DPI and text on a local
  console or a physical Windows machine before relying on them.
- **The meter's window is deliberately Windows only.** Linux has no GTK
  wakeup for it (`g_idle_add` or similar through purego would be the next
  step). On Linux, `-meter` works only with `-png`.
- **Live state:** Michael auditioned the real window, and every check but
  DPI "looked great". He can't change display scaling on this host, so DPI
  handling (`WM_DPICHANGED`, scales other than 100%) is still untested. Test
  it on a machine where scaling can change. The text check had no recorded
  side-by-side reference app, so it is not a judgment against a matched
  Windows renderer.

## Handoff to the Linux session

After Michael commits on Windows and the branch arrives, in a clean worktree
of `spike/windows-native`, from `experiments/text-spike`:

1. `CGO_ENABLED=0 go test ./... && CGO_ENABLED=0 go vet ./...`. Linux has
   no Windows-only tests. `TestRewrapKeepsSpaces` and the meter-feed tests
   should pass.
2. `CGO_ENABLED=0 go build . && CGO_ENABLED=0 go build ./compare`, then
   run `go run ./compare -out /tmp` and check that it still writes both
   PNGs. Its only change is the `//go:build linux` line.
3. `GOOS=windows GOARCH=amd64 CGO_ENABLED=0 go build -o /tmp/spike.exe .`
   (amd64 is the only architecture tested).
4. Smoke-test the GTK window. Text, zoom, `0` and `q` should behave as
   before. The changes it shares: `app` now carries `bg`/`fg` (`-light`)
   and per-paragraph sizes (`-sizes`). The GTK window doesn't handle `l` or
   `s`, deliberately. `-meter` without `-png` should refuse with an error.
5. `go run . -png /tmp/m.png -meter -scale 2` should write a frame with the
   meter row.

From Windows, these were verified only as `GOOS=linux go vet`/`go build`
cross-builds. Neither the Linux window nor `compare` was run. If any step
can't run, say so in text.md's Windows section instead of letting it pass
silently.
