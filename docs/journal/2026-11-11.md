## Webview feasibility spike: Linux

Probes and evidence are in `experiments/webkitgtk-spike/evidence/linux/integration-feasibility/`, with the shared pieces in `experiments/webview2-spike/feasibility/`. All uncommitted; root framework, mixer and canon untouched. Windows has run nothing; its handoff is `experiments/webview2-spike/evidence/windows/integration-feasibility/README.md`.

- **The JSC signal problem is bigger than SIGUSR1.** Once JSC initializes in the Go process it also replaces Go's SIGSEGV and SIGBUS handlers (no `SA_ONSTACK`, chaining on the faulting stack), so any recovered Go fault, such as a nil dereference in an HTTP handler, becomes fatal. Moving the GC signal does not fix that. Working order: release an RT signal from Go (`signal.Ignore`, then `SIG_DFL`, since JSC warns about and replaces even `SIG_IGN`), call the private `JSConfigureSignalForGC`, force JSC initialization, then add `SA_ONSTACK` to JSC's fault handlers only. **Never add it to the suspend signal**: JSC suspends only threads whose stack pointer lies within their own stack, and the probe hung 3 of 10 runs. Production readiness waits on Michael's decision about the private symbol and adjusting another library's handler flags.
- Destroying a WebKit context inside an async completion crashes later. The `GTask` is freed after its callback returns and finalizes its source object, such as the cookie manager. Defer destruction by one main-loop iteration after the last completion.
- Custom URI schemes report no HTTP method in `decide-policy`, so the probe treats in-process form navigations as POST for Retry, GET forms included.
- Test servers that should look "down" must close connections. `ThreadingHTTPServer.shutdown()` leaves WebKit's keep-alive connection served, and a "failed" load then succeeds.
- `exitwatch.py` names adopted-but-unsampled children from their zombie `comm`. Earlier "unobserved SIGKILL" failures were bwrap helpers it could not see. Don't read the first B–D run's child failures as browser crashes.
- Live state: Michael's manual check of the error page's two buttons is pending. Final results are on 2.52.6, which lacks the graphics-teardown fix; no supported fixed runtime is installed. Linux recommendation: native content filter as primary enforcement, guard CSP second, ephemeral sessions, no profile directory. Windows probes must be written and run on the Windows host before mechanisms are reconciled and the integration spec is revised.

## JSC signal reservation follow-up

- Michael kept Linux production readiness pending and had the signal choice investigated first. Inferring JSC's GC signal is withdrawn. In a Go process a `signal.Notify` subscription is invisible: the kernel shows Go's handler on subscribed and unsubscribed signals alike, and `os/signal` cannot list subscriptions. The inferred selector picked an undeclared subscriber's signal, `signal.Ignore` cancelled that subscription silently, and raising the signal after JSC took it killed the process in 8 of 10 runs. Evidence: `experiments/webkitgtk-spike/evidence/linux/integration-feasibility/signals-reservation/`.
- The prototype (`-signal-reserve N`, experiment only, no dfx2 API) requires an explicit application reservation and refuses without one. Its checks are sanity checks: none can see a Go subscriber, and the post-initialization audit only detects a later `Notify` after the fact. Correctness depends on the application keeping its promise; don't describe the checks as verifying it.
- Go's signal table leaves 32–34 to libc (34 is musl's `SIGSYNCCALL`), so `SIGRTMIN` (34) has a default disposition and is not available; reservations start at 35. Don't treat "default" as free.
- Not in scope and unchanged: the suspend handler on goroutine stacks, the fault-handler flag change, SIGXCPU, and the private-symbol decision. The 2.54.2 comparison libraries were lost from `/tmp` in a reboot. Nothing committed; awaiting Michael's review.

## JSC handler safety follow-up

- **Result: the in-process approach cannot give a compatibility contract.** A thread that takes a JSC VM's API lock stays registered for conservative scanning until it exits. Once its call returns and heap access is released, JSC's collector or `HeapHelper` threads suspend it on every scan. When that thread is running Go, the suspend handler (no `SA_ONSTACK`) sees a stack pointer outside the recorded OS stack, declines, and `Thread::suspend` re-sends without bound. The traced probe: 527 deliveries to the main thread during Go phases, none during C. Each delivery pushes a kernel frame of at least 2,032 bytes (`AT_MINSIGSTKSZ` here) onto a goroutine stack guaranteed only 928 bytes, so this is silent memory corruption risk, not a reported fault. `SA_ONSTACK` makes suspension impossible, which is why the earlier `configured-onstack-all` probe hung. UI-thread-only use does not help: the UI thread is the registered one. Evidence: `experiments/webkitgtk-spike/evidence/linux/integration-feasibility/handler-safety/`.
- The combined multi-window host run was deliberately not done, per the brief's stop condition. The earlier passes B–D ran with a host JSC VM (the `js` command), so they remain browser-policy evidence only, not evidence of signal safety.
- SIGXCPU is `WTF::sigxcpuHandler` (`RealTimeThreads.cpp`), installed once from the main loop after WebKit registers a real-time `WorkQueue` thread. It appeared with WebKit initialized first, not with JSC first; that difference is unexplained. Symbolized with Ubuntu's debuginfod file for build ID `e01f2b5c…`, kept in `/tmp` and out of git.
- The narrow, identity-verified SIGSEGV/SIGBUS adjustment works and refuses unidentified handlers. It addresses only the fault handlers. Untested direction worth Michael's decision: never create a JSC VM in the Go process (no JSCValue-producing APIs, which fits the no-JS-RPC design). Linux readiness, the private symbol and handler modification all remain unapproved. Nothing committed.

- Michael approved the no-host-VM investigation next. The negative result above rules out the host-VM workaround, not yet in-process HTTP dispatch or all WebKit integration. Replace native JS-result automation with page-driven handler reports, validate VM/thread-registration instrumentation with a separate positive control, and trace required WebKit paths. Do not pursue per-call signal-mask changes or reuse the fault-handler patch. SIGXCPU/private-symbol approval and Linux readiness remain open; Windows work is unstarted.

## No JSC VM in the Go host

- **Result on 2.52.6: the required paths are VM-free.** The no-host-VM investigation found no JSC VM, GC thread registration, suspension or fault-handler finalization in the Go host. Covered: cookies, filters, storage, navigation and redirects, clicked error-page actions, both transports, inspector, teardown, and a two-window combined run. Seen from outside by gdb (`vmwatch_gdb.py`), validated by two positive controls. Evidence: `experiments/webkitgtk-spike/evidence/linux/integration-feasibility/vm-free/`.
- **The one host-side VM path is `JavaScriptEvaluationResult::toJSC` → `API::SerializedScriptValue::deserializationContext()`**, a process-wide lazy `JSGlobalContextCreate` on the main thread. JavaScript results, script messages (a reply's destructor too) and `get_javascript_global_context` all reach it. The first VM runs `Config::finalize` once per process, so one stray call installs JSC's fault handlers permanently. Any future dfx2 Linux webview code must never call those APIs. The feasibility host's `js` command is exactly such a call.
- `vmwatch_gdb.py` needs Ubuntu's debuginfod files. The watched JSC functions are local symbols, and without the debug file the breakpoints resolve to nothing and the monitor reports silence. Each run checks resolution; keep that check. Debug files live in `/tmp` (JSC build ID `e01f2b5c…`, WebKit `97884928…`) and vanish on reboot.
- Loopback handler counts are not navigation counts. One `/api/abort` navigation reached the Go handler 1–3 times, apparently the network layer re-sending over dead kept-alive connections (unverified). Judge Retry by `navigation-allowed` events. The first recorded `combined` run failed on exactly this and is kept beside its rerun.
- Still open: JSC's suspend handler is installed by WebKit's own `JSC::initialize`. It needs the reservation, which needs the unapproved private symbol, and without one it takes SIGUSR1. SIGXCPU is installed in every host. The manual error-page check is pending. Linux readiness is unapproved, and Windows is unstarted. `feasibility.py`'s old suite was not rerun after its additive changes (wrappable `Host`, attach `/api/report`, `<title>` on 404/500). Nothing committed.
