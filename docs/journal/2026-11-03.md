- **Leave the `//go:uintptrescapes` on `com.call` and `callProc` (`com_windows.go`, `host_windows.go`).** Call sites pass `uintptr(unsafe.Pointer(&out))` through these variadic helpers. Without the directive, `out` can stay on the stack and move when the stack grows, leaving native code writing to the old address. It's the same mechanism `syscall.Proc.Call` relies on.
- **`Dispatcher.work` calls `wake` with its lock held, deliberately.** That's what makes "no post after `Close` returns" true, so the host may destroy the window (and Windows may reuse its handle) right after `Close`. Moving the post outside the lock reopens that race.
- **The hide-and-wait close branch (`envPending` in `beginClose`, `timerEnvWait`) is untested, not dead.** On this host, the environment callback always runs inside `CreateCoreWebView2EnvironmentWithOptions`, so close can't land during environment creation. The API is documented as asynchronous, so another Runtime or host may reach the branch. Keep it.
- **`watchConsole` exists because of a real failure.** Michael's first manual windows were launched from the agent's console and died together with `0xC000013A` when that console went away: no close path ran. Ctrl+Break is now tested. Console close, logoff and shutdown (`SIGTERM` in Go) are not.
- **Couplings:**
  - `bindings.go` slots ↔ `TestBindingsMatchIDL` (only meaningful with `WEBVIEW2_IDL` set).
  - `loaderSHA256` in `host_windows.go` ↔ the pins in `setup-loader.ps1` and the README. A new SDK changes all three.
  - `fixture.Binary` ↔ `expectedBinary()` in `app.js`.
  - `adapt.Limit` ↔ `LIMIT` in `app.js`.
- **The SDK pin is 1.0.4129.50 because it matches the Runtime's build (151.0.4129.93),** not for any feature. The host uses only v1 interfaces. A newer SDK should be fine, after re-running the IDL test.
- **Don't detect the Runtime by the `EdgeUpdate\Clients` registry key.** It's absent on this host, yet the Runtime is present; the loader finds it.
- **Agent tooling on this host:** in the Bash tool, `/c/...` is `C:\Cygwin64\c\...`, not `C:\`. Use `/cygdrive/c/...` or PowerShell.
- **Files written on this host look executable to git.** `git` here is Cygwin's (`C:\Cygwin64\bin\git.exe`), the repository's `.git/config` sets `core.filemode=true`, and Cygwin maps the NTFS permissions of new Windows files to 755. Every new file in this change was `chmod 644`'d through Cygwin, so `git add` records 100644; check with `git add -N … && git diff --summary` before committing. **Not fixed, deliberately:** `cc6e2f1` already committed 14 text-spike and doc files as 100755 (`git ls-files -s | grep ^100755`).
