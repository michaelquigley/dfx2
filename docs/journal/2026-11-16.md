## Windows body-read probe (same day, Windows host)

The probe ran in `experiments/webview2-spike` (`-feasibility -feas-body`, `evidence/windows/body-probe/`); root code unchanged. What the next agent should not rediscover:

- **Every incoming request body stream on Runtime 151.0.4129.93 is agile** (`IAgileObject` S_OK, free-threaded marshaler, `Stat` reports the full length at position 0). Reads on a locked `COINIT_MULTITHREADED` thread are byte-exact and complete while the UI thread is asleep without pumping, so they really run off the UI. The marshal fallback was never taken: it has no native evidence, so production should refuse a non-agile stream rather than rely on it.
- **The intercepted request carries no `Content-Length`**; `Stat` is the only up-front length. A `ReadableStream` request body arrives with no content at all (handler sees 0 bytes, page sees 200): the transport drops it silently and interception cannot tell it from an empty POST. That is a spec question, not a threading one.
- **A stream stayed readable 32 ms after its deferral was completed and a 503 installed** (the close landed mid-read once in four tries). Good for the close design; no evidence about longer survival.
- **The ~6.5 s browser-process exit correlates with network activity in flight at close** (three windows closed during their page's navigation or fetch: 6.5 s; one closed at rest: 275 ms). Same number stage 3 saw after `quit`; still not a timeout to add.
- Decided: the probe lives in the spike's feasibility host behind `-feas-body` (empty flag is the unchanged UI read) rather than a new experiment, so it reuses the host, page and driver; the gate stream is the spike's own 14-slot IStream, not production's.
- **Live state:** probe complete, five scenarios pass; stage-3.md has the results and the smallest production change they support; the production fix is not implemented. Nothing is committed.
