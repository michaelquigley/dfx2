# Webview content

The `webview` package opens browser windows that share the application lifetime with native windows, in explicit in-process, owned loopback or attached-URL modes. Linux/amd64 hosts them in WebKitGTK 4.1 ([below](#linux-host)), validated natively in [stage 2](../../evidence/webview-integration/stage-2.md). Windows/amd64 hosts them in the system WebView2 Runtime through a loader embedded in the executable ([below](#windows-host)). Native validation in [stage 3](../../evidence/webview-integration/stage-3.md) covered the returned revision (`d328fbb`), which read request bodies on the UI thread. The [corrections since](../../evidence/webview-integration/stage-3.md#return-corrections--2026-11-20) have modeled tests and Windows cross-builds only, and await native Windows validation. They cover the worker body reader, close during a read, response-stream-gated teardown, failures reported during close, and the declaration and body-stream contract. Every other target refuses with `webview.ErrUnsupportedContent` before any native work, and nothing is latched. The portable contracts (modes, attachment boundary, core ownership, the finite in-process adapter and the owned loopback server) are tested against fake native seams in [stage 1](../../evidence/webview-integration/stage-1.md).

The [runtime contract](runtime.md) still governs lifetime, threads, posting, failure and shutdown. This document covers only what browser windows add.

## Programming model

```go
w, err := webview.Open(app, webview.Options{
	Window:  dfx2.WindowOptions{Title: "Mixer", Width: 760, Height: 520},
	Mode:    webview.InProcess,
	Handler: mux, // an ordinary http.Handler, serving from "/"
})
```

`webview.Window` forwards `Close`, `Context`, `Done`, `SetTitle`, `Post` and `Go` with their documented thread rules. It exposes no native handles, readiness, navigation or JavaScript calls.

Every window chooses one mode, and nothing falls back between them:

| Mode | Required | Rejected | Owns |
| --- | --- | --- | --- |
| `InProcess` | `Handler`; optional `Limits` | `URL`, `Origins`, `Server` | The browser and every request it admitted |
| `Loopback` | `Handler`; optional `Server` | `URL`, `Origins`, `Limits` | The browser, its server, connections and handlers |
| `Attach` | `URL` (absolute http or https, no user information) and `Origins` including the URL's own | `Handler`, `Limits`, `Server` | The browser only; never the service |

`LinuxGCSignal` names the real-time signal the application reserves for WebKit's garbage collector; Linux requires it ([below](#the-reserved-gc-signal)) and other platforms ignore it. The zero `Mode` is invalid. Origin entries are origins alone (scheme, host, optional port); a path, query or fragment is rejected. Origins are parsed and canonicalized with explicit effective ports, then compared as parsed origins, never by string prefix. `DevTools` enables the engine's inspector, for auditions; it is off by default.

## Opening, readiness and closing

A nil app is an immediate argument error. On a valid app, the wrong thread returns `dfx2.ErrWrongThread` and a closing app `dfx2.ErrClosed`, as operation errors. Invalid options and invalid dimensions are checked next, before any resource exists, and are returned and latched as application failures, as `NewWindow` does with its own. A platform without browser hosting refuses after that with `ErrUnsupportedContent`, before native work, and latches nothing; a starting window it refused is rechecked for last-window shutdown.

Otherwise the native shell is created and the window is live at once. In order, the core then obtains the shell's private parent descriptor, starts the endpoint (binding the loopback listener), creates the browser attachment and starts it. Any failure along that path is a fatal opening error, returned and latched; whatever was already acquired drains through the ordinary close path. `Open` returns once the attachment has started; the browser initializes asynchronously and asks the core before it navigates. The core refuses that navigation once the window is closing, so a late initialization result is released rather than navigated. A close that arrives during shell or browser creation skips the remaining steps: the browser is never created or never started.

Close cancels the window context at once. The endpoint's admission and sealing share its lock and its context is the window's, so no request is admitted after close. On the UI thread, the core then closes the endpoint and the browser while the shell is still valid. The shell is destroyed only after the browser reports that no native object or callback still uses it. The window record, and `Done`, wait until the browser has released, the endpoint reports that everything it admitted has returned, every published completion has settled and every cleanup task has finished. A handler that ignores cancellation therefore keeps `Done` and `Run` pending, and visible.

Browser windows count as live for last-window shutdown from the moment the shell is registered. They are not enrolled in frame or input scheduling: copied size and scale notifications are forwarded to the attachment as bounds.

## Failure tiers

An HTTP error status and a rejected application command are page results. Unexpected browser failures, reported by the attachment, are fatal: the application cancels and drains, and the error reaches `Run`, beside any earlier failure rather than behind it. Endpoint failures are kept the same way: a loopback listener failure reported before drain, or an owned handler's panic, reaches `Run` beside an earlier failure. A shell destroyed while its browser still used it is the same kind of failure, and the browser still drains. An unexpected panic in an owned handler, in either owned mode, is an application failure with its stack; the page never sees the stack. `http.ErrAbortHandler` is a deliberate request abort and a deliberately returned 500 is an ordinary response; neither fails the application.

Post-release cleanup, such as removing a temporary profile directory, runs off the UI thread as owned work registered by the attachment before it releases. Unexpected cleanup errors and recovered panics cancel the application and remain in `Run`'s result alongside earlier failures; panics retain their stacks. The sole nonfatal exception is an explicitly identified file-deletion residue after native users have released the files and bounded deletion attempts have finished. Its path and cause remain in `Run`, but other windows keep running. The window stays registered until cleanup returns. The private attachment must return `platform.FileDeletionResidue` directly with a nonempty path and cause; wrapping or joining it does not exempt other failures, and panicking with it is still fatal.

## In-process adapter

The browser routes native requests by window to the core, which forwards them to the window's adapter on the UI thread. The adapter admits or refuses, copies the request into Go-owned values and starts the handler on a worker; it never calls application code on the UI thread. The worker's result is published through a completion registered before the worker started, and settled on the UI thread even while closing. A result for a closing window, or for a request the browser already released, is discarded rather than delivered.

Limits per endpoint; zero selects the default:

| Limit | Default | Failure |
| --- | --- | --- |
| Request body | 1 MiB | 413 |
| Response body | 1 MiB | 502 |
| Request or response metadata | 64 KiB (minimum 1 KiB) | 431 / 502 |
| Admitted requests | 16 | 503 |
| Aggregate adapter-owned buffers, native copies included | 64 MiB | 503 |

Metadata is measured before the URL is parsed, and charged as the UTF-8 bytes of the method and URL (or status) and every header name and value occurrence, plus 64 bytes per record and 64 per header occurrence for the Go structures that hold it. A response is measured on the handler's own header map before the adapter copies anything, so oversized metadata is never copied. The copy then owns its strings: every name and value is copied, so a short header sliced from a larger string cannot keep that allocation alive past the measured bytes. Entries with nil or empty value slices still charge their names and entry overhead because the snapshot retains them, even though they emit no header field. The aggregate reservation additionally includes eight URL-input lengths plus 1 KiB for decoded/escaped URL forms, origin canonicalization, RequestURI construction and fixed URL/request structure overhead. This conservative allowance is reserved before cloning or parsing, retained until final request release, and rolled back on refusal. The origin check reuses the parsed URL. The public metadata ceiling still measures the incoming representation; neither it nor the aggregate budget is raised. The browser passes the declared `Content-Length` and whether the engine supplied a body stream as separate facts, and the endpoint applies one rule for both engines:

| Declaration | Stream | Result |
| --- | --- | --- |
| Above the body limit | either | 413 |
| Positive, within the limit | absent | 400, before any handler |
| Zero | present | one detection byte is read and nothing stored: EOF serves an empty body, a byte is 400 before any handler |
| Zero or none | absent | an empty body, served at once |
| None | present | the bounded unknown-length read |

Admission reserves a request's worst case before anything is buffered: its metadata and URL allowance, its body (the declared length, or the limit plus a detection byte when unknown), one native read buffer of at most 64 KiB, and a full response with its metadata, twice: as the Go result and as the browser's copy. Parts are released as their owners finish: the read buffer when the body ends, the body when the handler returns, the Go response (charged at its buffer's capacity) once the browser has copied it, the browser's copy when the browser releases the request. The admission slot and remaining bytes are released only when the browser and the handler have both finished, so an abandoned handler still holds them. A fixed transfer reserve of one metadata limit, also out of the buffer budget, covers the browser's transient request metadata for the one synchronous request call in progress: requests arrive one at a time on the UI thread, and a browser builds it only for a request within the metadata limit, measured by the same rule. WebKitGTK's is a header slice of native string views; WebView2's is UTF-8 copies of the method, URL, header names and values in an exactly sized slice. Either fits one limit, because string bytes are charged exactly and each slice entry is smaller than the 64 bytes charged per occurrence. With the defaults, sixteen worst-case requests fit the budget beside both reserves. Limits that are negative, that exceed the buffer limit individually, a buffer limit above 2^50 bytes, or limits that leave the budget unable to hold one worst-case request, are invalid options; the bounds keep every reservation sum exact in `int64`.

There is no queue: excess requests are refused at once. Refusals of requests that hold no admission (403 for a URL outside the endpoint's origin, 400 for a malformed request, 413, 431, 503) use one of 16 bounded slots reserved out of the buffer budget. With every slot in native delivery, the browser is told to abort the request instead, so even refusals cannot grow without bound. Failure responses are fixed and tiny; they never echo the request or a stack.

The body buffer is allocated once, at its reserved capacity, on the first read, so reading never holds two buffers at once; a body of unknown length therefore holds the full limit plus one byte until its handler returns. Body reads follow the declared length exactly: a body longer or shorter than declared gets 400, a read beyond the granted chunk or a failed native read aborts the request, and close cancels reads in progress. The handler sees `Method`, the path and query (`URL`, `RequestURI`), the request's headers, the finite body and `ContentLength`, `Host` from the browser-assigned origin, and the window context. The transport is synthetic: `RemoteAddr` is empty, `TLS` is nil, and there is no protocol negotiation, trailer or upgrade.

The `ResponseWriter` is buffered and offers neither `Flusher`, `Hijacker` nor `Unwrap`; `http.NewResponseController(w).Flush` reports `http.ErrNotSupported`. A body beyond the limit fails the whole response with 502, even if the handler ignores `Write`'s `ErrResponseTooLarge`; no successful prefix is ever published. Informational (1xx) responses, trailers and oversized response metadata also give 502. Headers are taken as they stood at `WriteHeader`; `Connection`, `Keep-Alive`, `Transfer-Encoding`, `Trailer`, `Upgrade` and the handler's `Content-Length` are dropped, `Content-Length` is set from the body, and an absent `Content-Type` is sniffed as `net/http` does. `HEAD` and bodiless statuses carry no body. An unexpected handler panic answers with a fixed 500 and fails the application; `http.ErrAbortHandler` answers with a fixed 502 and does not.

Reload and fetch abort do not cancel handlers: the browser releases its request and the handler keeps its admission until it returns. Close is the reliable cancellation boundary.

## Owned loopback server

Each window owns one server on `127.0.0.1` with an assigned port, serving ordinary HTTP: request bodies stream under the handler's control, and responses stream with no finite limit, write deadline or mandatory buffering. The `ResponseWriter` offers `Flusher` (and `FlushError`), never `Hijacker` or `Unwrap`, so no handler can take an unowned connection. Upgrade requests are refused with 501. The server's error log is discarded.

| Limit | Default | Failure |
| --- | --- | --- |
| Request header bytes | 64 KiB | `net/http`'s 431 |
| Header read timeout | 5 s | connection closed |
| Idle timeout | 30 s | connection closed |
| Live connections | 32 | closed before being served |
| Concurrent handlers | 16 | 503 |

Each endpoint generates a random 256-bit secret, which the browser is to install as an HttpOnly session cookie named `dfx2_endpoint`, scoped to the endpoint's origin, before its first navigation. Before any handler runs, the access layer requires that cookie (compared in constant time), the exact `Host` including the port, and, when an `Origin` header is present, exactly the endpoint's origin. A missing `Origin` is accepted only with both of the others. A request failing any check gets 403 without reaching the handler. The secret never appears in URLs, page script or `Status`. Access checking is separate from how the browser receives its cookie; no other access policy exists yet.

Close stops the listener, closes every connection the endpoint accepted and cancels request contexts. It does not wait: connections are counted from acceptance until closure and handlers from entry until return, independently of the server's shutdown bookkeeping, and the endpoint reports drained only when the serve loop, every connection and every handler have finished. Any accept failure other than the listener's own closing (`net.ErrClosed`) or a temporary error, which `net/http` retries, is fatal, even when it overlaps the window's close. It is captured at `Accept`, because `net/http` reports `ErrServerClosed` once shutdown has begun, and it is reported before the endpoint can report drained. A handler panic answers with a fixed 500, its staged headers discarded, or aborts a response already under way, and fails the application. Closing one window's endpoint never touches another's.

## Owned-response security policy

Every response produced through either owned endpoint adapter, including its fixed failures, carries this framework `Content-Security-Policy`:

```
default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self'; font-src 'self'; connect-src 'self'; media-src 'self'; object-src 'none'; frame-src 'none'; child-src 'none'; worker-src 'none'; manifest-src 'self'; frame-ancestors 'none'; form-action 'self'; base-uri 'self'
```

It is added after the handler's own headers, as the response is committed, so a handler can add its own policies, which browsers enforce as well, but cannot remove or relax this one. For a loopback handler that returns without writing, the wrapper adds the policy before net/http sends its implicit 200 response. A loopback handler's informational responses, such as 103 Early Hints, are not forwarded, because they would reach the page without the policy. The in-process adapter refuses them as well. A 101 is committed with the policy as before, and net/http's own automatic 100 Continue is unaffected. It permits no inline script or style, no objects, frames or workers (service workers included), and no external form targets. Attached services receive no framework policy, credential or access layer.

Standard-library protocol errors sent before the loopback endpoint handler runs are a narrow exception: Go may send plain-text or bodyless rejections, such as malformed-request 400s and oversized-header 431s, without the framework CSP. They never reach the application handler. dfx2 does not replace the HTTP parser or rewrite raw connection output to add a header to those errors. The exception does not apply to application responses with the same status codes, implicit successful responses or the adapters' fixed failures, and does not relax native browser confinement.

## Private boundaries

`internal/platform` describes browser hosting with plain data and interfaces: content kinds (plain, drawn, browser), the browser-parent descriptor a backend supplies for a live browser shell, the browser configuration (mode, start URL, allowed origins, loopback credential, inspector), the factory and attachment, the host the core provides to it, in-process request and response values, and the audit snapshot both hosts report for internal auditions. It imports no core, HTTP or content package. Browser factories are selected only by the `webview` package, so native-only applications never reach them. GTK creates browser shells, toplevel windows whose container the attachment fills; Win32 creates them as plain top-level windows whose HWND the attachment's controller fills, draws nothing in them, delivers them no input but focus, and re-reports their unchanged surface after a move. The WebKitGTK attachment lives in `internal/platform/webkit` and the WebView2 attachment in `internal/platform/webview2`; each imports the platform contract and `internal/origin` only. `internal/endpoint` holds both adapters and imports no native types; `internal/origin` canonicalizes origins for the adapters and the browser's navigation policy. The root package reaches none of `webview`, `internal/endpoint`, `internal/origin`, `net/http` or either browser package; the dependency test enforces it.

Every attachment method runs on the UI thread except `Diagnostics`, which the shutdown supervisor calls while the UI thread may be stalled. Each request ID a browser receives from admission owes exactly one release, whatever the decision. Neither the core nor the adapters hold their locks while calling the other or the attachment, so reentrant notifications are safe. An attachment that implements `platform.BrowserFocuser` is told when its shell gained keyboard focus; WebKitGTK does not need it, WebView2 does. Shutdown diagnostics add, for each browser window, its attachment stage, endpoint status, cleanup names and the attachment's own summary; `Inspect` counts browser windows and running cleanups.

## Linux host

Requirements: Linux/amd64 with GTK 3, libsoup 3 and WebKitGTK 4.1, 2.40 or newer (request bodies for in-process POSTs), loaded with `CGO_ENABLED=0` through purego. Validated on the installed WebKitGTK 2.52.6. The libraries load on the first `webview.Open`, never at application startup: an application that opens only native windows maps no WebKit or JavaScriptCore library, and the dependency test keeps the browser package out of the root's imports. A missing library or entry point is an initialization failure naming it, fatal like any other. No new version floor applies.

The attachment runs in the GTK backend's main loop. Its native callbacks use five permanent purego trampolines routed by numeric tokens; response storage, signal handlers and async operations carry tokens, never Go pointers. The Go process creates no JavaScriptCore VM: it binds no JavaScript evaluation, result conversion or script-message API, whose first use would install JavaScriptCore's fault handlers in this process. Page JavaScript runs only in WebKit's child processes.

### The reserved GC signal

JavaScriptCore installs a thread suspend/resume handler on its GC signal, SIGUSR1 by default, at WebKit's first type initialization. On Linux the application must therefore set `Options.LinuxGCSignal` to a real-time signal it reserves; it is never chosen automatically, and a missing or negative value is an invalid option. Before the first WebKit object exists, the host checks that the signal is within libc's real-time range, still carries the Go runtime's handler (no other component installed one), is not blocked on the UI thread, is not ignored through `os/signal`, and agrees with `JSC_SIGNAL_FOR_GC` if that is set. It then releases the signal from Go (`signal.Ignore`, then the default disposition) and passes it to JavaScriptCore's private `JSConfigureSignalForGC`. A missing entry point, a failed check or JavaScriptCore refusing the signal refuses initialization visibly; once Go has released the signal a failure is permanent for the process. The first reservation lasts for the process, through every window's close, and every later window must name the same signal.

These are sanity checks: none can see a Go `signal.Notify` subscription. The application promises that neither it nor its dependencies use, subscribe to, ignore, reset or send the signal. The mechanism moves JavaScriptCore's handler; it does not make a stray delivery safe. Any signal delivered on it kills the process. On the installed 2.52.6, WebKit also replaces Go's SIGXCPU handler. Both remain the monitored compatibility risk recorded in the work order; there is no runtime monitor, handler patch or helper process.

### Sessions and storage

Each window has its own ephemeral `WebKitWebContext`: its own cookies, local and session storage, cache and network process, kept in memory and gone when the window's context is released. Reload keeps them; reopening starts fresh. Nothing is written as a browser profile. The one on-disk resource is the window's compiled content filter, in a framework-owned `dfx2-webview-filter-*` directory under the temporary directory, removed off the UI thread after the attachment has released it, with 20 attempts 100 ms apart; a directory that still cannot be removed is the nonfatal named residue described above. A crash can leave such directories; nothing sweeps them.

### Confinement

Owned windows stay on their origin through three mechanisms together:

- **A native content filter** installed before the first navigation: every load outside the window's origin, and every child-frame document, is blocked inside the web process before a request leaves it. Attachments get only the child-frame rule; their subresources are the service's business.
- **The framework security policy** on every owned response, above.
- **Navigation policy**: top-level navigations, redirects included, to any origin outside the window's (for attachments, outside the declared origins) are ignored. New windows are refused, `window.open` cannot open windows automatically, permission requests are denied, responses the view cannot display (which would become downloads) are ignored and downloads are canceled. Download cancellation depends on the context's `download-started` signal: if it cannot be connected, browser creation fails and unwinds, like a required view signal.

Loopback windows install the endpoint credential as an HttpOnly, SameSite=Strict session cookie for `127.0.0.1`, through the window's cookie manager. The first navigation waits for both the filter and the credential, then asks the core; a closing window never navigates, and a late filter or credential result is released. Cookies ignore ports, so per-window sessions are what keeps two loopback windows' credentials apart.

### In-process transport

In-process windows load the custom scheme `dfx2://app`, registered per context as secure and CORS-enabled; each window's own context routes its requests to its own endpoint, so another window cannot reach it by naming the origin. The browser hands the endpoint views of WebKit's own method, URL and header strings, not copies; WebKit keeps them alive until the synchronous request call returns, and the endpoint copies what it retains before then. It first measures the request's metadata natively, allocating nothing and stopping once the endpoint's metadata limit (which the endpoint supplies when it starts) is exceeded; an oversized request reaches the endpoint with only its measured size and no headers, and is refused with the documented 431. Within the limit, the header slice is built at its exact size. The method is GET when WebKit reports none. The declared body length comes from `Content-Length` when present (otherwise unknown), and whether WebKit supplied a body stream is passed separately, so the endpoint can refuse a disagreement. Request bodies are read asynchronously in the chunks the adapter grants; the UI thread never waits on a body stream. Responses are copied into `g_malloc` storage owned by a GBytes; the request counts as released only when WebKit drops that copy, so the adapter's native-copy accounting holds until then. Closing fails every waiting request and cancels reads in progress.

WebKitGTK limits this transport, as observed natively and accepted for Linux stage 2:

- **Redirects are not followed.** A 3xx response from the custom scheme reaches the page or fetch as the 3xx itself; a top-level redirect leaves the window on a blank page on its own origin. Applications that need redirects use loopback.
- **No cookies.** WebKit stores no cookies for the custom scheme: `document.cookie` and `Set-Cookie` have no effect. Local and session storage work.
- **No load failures from handlers.** An in-process handler always produces a response (a deliberate abort gives a fixed 502), so the error page below arises in practice only for loopback and attached windows.

### Load-failure page

A failed top-level load, other than the host's own refusal or a cancellation, is replaced by a framework-local page with no script, the failing URI escaped and no credential. On WebKitGTK the host's refusals surface as `WebKitPolicyError` 102 (frame load interrupted by a policy change), and only that code is treated as a stopped load. WebKit's other policy failures, such as a URI or MIME type it cannot show or a restricted port, get the error page. Its Return to start action loads the configured start page with GET; Retry appears only when the failed navigation's final method was a known GET, so a 303 after a POST can be retried while a failed POST, a 307-preserved POST or an in-process form submission (whose method WebKit does not report) cannot. Actions are `dfx2-error:` links with a per-failure nonce, intercepted by navigation policy before any load; each failure's actions work once, and a later allowed navigation (even to the same URI) or close invalidates them. Methods are remembered per URI for the last 16 allowed navigations, so a subframe's navigation cannot rewrite the main frame's. Error-page actions never resubmit a form, but a browser may itself resend a request whose connection closed without a response before any action; judge Retry by navigations, never by server counts. HTTP error responses, 404 and 500 included, display normally.

### Failures and release

Initialization errors from environment creation, controller creation and credential verification remain fatal when their completion arrives during close. A successful late environment is not retained, and a late controller is closed without being attached. No HRESULT is silently treated as our cancellation: creation keeps its parent alive, and a completion released without invocation settles through the dropped-handler path. Missing results and failed credential checks remain errors too. Browser failures received after an earlier application failure remain in `Run`'s result.

A web process terminating at any point before the view is destroyed, closing included, is a browser failure: fatal, with no restart. The host never terminates a web process itself, and destruction disconnects the signal first, so ordinary teardown cannot raise one. An initialization failure (filter, credential, temporary directory) is fatal too, including one that completes after close has begun: only GLib's own cancellation (`G_IO_ERROR_CANCELLED`), which close causes, is silent then, and a filter that saved anyway is released without being installed. Close cancels the window's native operations and requests, stops loading, then destroys the view on a later main-loop turn, once every owed async callback has run: a GTask releases its source object only after its callback returns, and destroying the context from inside one crashed WebKit 2.52.6 later. The attachment reports released only when the view is destroyed and WebKit holds no request or response copy; the shell is destroyed after that. WebKit's own processes are not part of that drain: the matrix observes them exiting with the host, and `bwrap` sandbox helpers end with SIGKILL when the host exits, by their `--die-with-parent` design.

Diagnostics report the runtime version, the reserved signal, the attachment's stage and its native requests, reads, response copies and pending callbacks.

## Windows host

Requirements: Windows/amd64 with the Evergreen WebView2 Runtime installed (Windows 11 includes it; Windows 10 needs the installer from <https://developer.microsoft.com/microsoft-edge/webview2/>), built with `CGO_ENABLED=0`. The stage 3 return was validated on Windows 10 (10.0.19045) with Runtime 151.0.4129.93; the corrected tree has not yet run natively ([Windows handoff](../../evidence/webview-integration/stage-3.md#windows-handoff)). The application is one executable: the pinned x64 `WebView2Loader.dll` from SDK 1.0.4129.50 (SHA-256 `a9a09232c25805323d4cfb3fc8f545a190a9c8a99c93262ea99d0b88df99ec90`) is embedded in `internal/platform/webview2` together with its `LICENSE.txt` and `NOTICE.txt`, which the loader's BSD-style license asks every binary distribution to reproduce; `internal/platform/webview2/sdk/` holds the files, every Windows executable that links the package carries the texts byte for byte (the code that hands out the loader keeps them reachable, so the linker cannot drop them; a test cross-builds the example and checks), and this document records the terms. Nothing is downloaded, no SDK file is read beside the executable, and no helper executable exists. The system Runtime is not bundled: a missing Runtime is an initialization failure naming the installer, fatal like any other, after the loader has been unloaded again.

Native-only applications touch none of it: the first `webview.Open` initializes COM on the UI thread (apartment-threaded; a thread already in another apartment is an initialization failure), writes the embedded loader into a fresh `dfx2-webview2-loader-*` directory under the temporary directory, verifies the written file's digest, loads it by that absolute path alone, and asks it for the Runtime version. The loader stays loaded while any browser window lives. The last window's release unloads it and removes its directory through the same off-UI-thread cleanup, bounded attempts and named residue as profiles; a later window extracts a fresh copy. The dependency test keeps the browser package out of the root's imports.

### Sessions and profiles

Each window has its own WebView2 environment over a fresh `dfx2-webview2-profile-*` directory under the temporary directory: its own cookies, local and session storage, cache and browser process (`msedgewebview2.exe`). Reload keeps them; reopening starts fresh. The runtime reports the profile it actually uses (`ICoreWebView2Profile::ProfilePath`); a path outside the window's directory, as a `WEBVIEW2_USER_DATA_FOLDER` override would produce, is a fatal initialization failure rather than a shared profile. The directory is deleted off the UI thread, with 20 attempts 100 ms apart, only after the environment's `BrowserProcessExited` event has reported the window's browser process gone and every WebView2 object and handler has been released; a directory that still cannot be removed is the nonfatal named residue described above. There is no timeout on the exit event: a browser process that never exits keeps the window pending, visibly, in the shutdown diagnostics. A crash can leave such directories; nothing sweeps them.

### Confinement

Owned windows stay on their origin through three mechanisms together, and the first two are both load-bearing, as the feasibility spike established:

- **Native interception** of every request in every resource context (`AddWebResourceRequestedFilter("*", ALL)`): a request outside the window's origin, redirects and cancelled navigations included, is answered inside the browser with a fixed 403 and never leaves it. This is the network boundary: on WebView2, cancelling a navigation does not stop its request.
- **The framework security policy** on every owned response, above. It is what stops a WebSocket handshake, which interception never sees.
- **Navigation policy**: top-level navigations, redirects included, to any origin outside the window's (for attachments, outside the declared origins) are cancelled; every child-frame navigation is cancelled; new windows are handled without opening one (`window.open` returns null); permission requests are denied; downloads are cancelled.

Attachments get the navigation, frame, popup, permission and download policy, observe document requests only (for the failed navigation's method below) and receive no interception, credential or framework policy; their subresources are the service's business, and a cancelled navigation's request may still reach its destination.

Loopback windows install the endpoint credential as an HttpOnly, SameSite=Strict session cookie for `127.0.0.1` through the window's own cookie manager (`AddOrUpdateCookie`, which is synchronous), then confirm with `GetCookies` that the manager holds it HttpOnly before asking the core whether to navigate. Cookies ignore ports; per-window profiles are what keep two loopback windows' credentials apart. The in-process origin needs no credential: its requests arrive through the window's own interception.

### In-process transport

In-process windows load `https://dfx2.invalid/`; the origin every in-process window names is `https://dfx2.invalid:443` in canonical form, and a handler sees `Host` as `dfx2.invalid:443`. Each window's own `WebResourceRequested` handler routes requests on that origin to that window's endpoint, so another window cannot reach the endpoint by naming the origin, and the `.invalid` top-level domain can never resolve, so a request that escaped interception would fail rather than reach a network host. WebView2 hands request strings over as native UTF-16 copies, which the browser must convert to Go strings, so it measures before converting: the method and URI first, then every header in a first pass, each by its exact UTF-8 length computed in place, the native copies freed as they are measured. A request past the endpoint's metadata limit has nothing converted: it reaches the endpoint with only its measured size and gets the documented 431, without an origin check or navigation record. Within the limit a second pass converts the headers into a slice of exactly the counted size; these copies are the transient metadata the endpoint's transfer reserve covers. The declared body length comes from `Content-Length` when present (otherwise unknown). Whether the engine supplied a body stream is passed separately, and only when `get_Content` succeeded; a failed getter keeps its request-local abort.

Request bodies are read off the UI thread. `get_Content` keeps its HRESULT: a null stream with success is an empty body, while a failed getter admits the request with an unknown length and aborts it, never serving it as empty. For a method other than GET or HEAD, a `request-content` event records the getter's HRESULT whenever it yields no stream, so an upload that arrives without content can be told from a failed getter. The event keeps only that result and nullness, never the request's URL or method, because it outlives the request call. Whether a `ReadableStream` upload arrives with a stream, a null one or a failure is not yet established. When the endpoint asks to read a body, the browser first asks the stream for `IAgileObject` on the UI thread. A stream that answers is read on its own worker: the deferral is taken and the read registered before it starts, and the worker, a goroutine locked to its own OS thread and initialized for COM's multithreaded apartment, reads one granted chunk at a time and posts each result through the private callback queue. Each read has one buffer, allocated within the endpoint's read reservation. It is passed by hand: in the grant to the worker, back with the result, and into the next grant, so the worker holds it only while a read is in flight. Once the endpoint's final decision consumes the last result, or close discards a queued grant or a posted result, nothing holds it. Endpoint decisions, browser state, event arguments and the deferral stay on the UI thread. The worker releases its stream reference before leaving COM. Only after `CoUninitialize` returns does it count as finished: the UI thread then drops the reader, and the request's release and the window's release may proceed. If COM initialization fails, the worker uses nothing and reports the failure once, and the UI thread releases the stream and aborts the request. Workers are bounded by admission (16 per window by default); there is no pool, no generic marshaling and no fallback to reading on the UI thread. A stream without `IAgileObject` is a request-local failure: the request is aborted without a response, so the page sees a network error and the handler never runs, and a `body-unsupported` event records the HRESULT. Every body stream observed on Runtime 151 declared `IAgileObject`.

Closing settles a reading request's native interception at once, completing its deferral without a response, and stops further reads without waiting. The worker claims each grant before it calls `Read`, and stopping is terminal: a grant queued but not yet claimed is never read, whether it is the first or a later one. Close records a `close` audit event, `claimed-reads=N`, counting the reads it stopped while claimed, the reads in flight at that boundary. A reader leaving COM, and one with a grant queued but unclaimed, is not counted. A claimed read is the one in flight, and the worker keeps its stream, its buffer and the endpoint's admission until the read in flight actually returns; its late result is dropped, never answered or navigated, and only then does the request count as released and may the window release. The same holds on every path, not only close. A request's release is reported to the endpoint once, after both its native ownership and its body worker have finished, in either order. Native ownership means the waiting deferral, an abort or a delivered response's stream. Until then the request keeps its admission slot. There is no forced termination and no timeout: a read that never returns keeps its window's `Done` and `Run` pending, visible in diagnostics, while the UI thread keeps serving other windows. A response is handed to WebView2 as an `IStream` the host implements over a copy of the body, agile and read-only, so the engine may read it from any thread; the request counts as released, and the adapter's native-copy accounting ends, only when the engine drops its last reference to that stream, wherever that happens. Fixed refusals are delivered the same way and hold their refusal slot until then. An aborted request has no response installed: it proceeds to its unresolvable host and fails there, so the page sees a network error rather than an HTTP status. Closing settles every waiting request the same way.

Redirects are followed and cookies work on this origin, unlike WebKitGTK's custom scheme. An in-process handler still cannot produce a load failure (a deliberate abort gives a fixed 502), so the error page below arises in practice for loopback and attached windows.

### Load-failure page

A failed top-level load, other than a refused or superseded navigation, is replaced by a framework-local document (`NavigateToString`, which navigates to a `data:` URI with an opaque origin; the navigation policy admits exactly that navigation while the document is pending) with no script, the failing URI escaped and no credential. Its actions are links into `https://dfx2-error.invalid/`, a host that cannot resolve, carrying a per-failure nonce; navigation policy cancels them before any request and acts on what the host recorded. Return to start loads the configured start page with GET; Retry appears only when the failed navigation's final document request was a GET, so a 303 after a POST can be retried while a failed POST or a 307-preserved POST cannot. Each failure's actions work once; a later allowed navigation, even to the same URI, or close invalidates them. WebView2 reports no method itself and, after a redirect, reports the redirect's HTTP status for a failed navigation, so the host correlates by generation: every top-level `NavigationStarting` (redirect hops included) begins one, each document-context request records its generation and method, and a `WebResourceResponseReceived` counts as "the server answered" only when its URI's latest document request belongs to the current generation. A fetch of the same URL, an older navigation's response and a redirect's status therefore cannot turn a failed load into a success. HTTP error responses, 404 and 500 included, display normally. A browser may itself resend a request whose connection closed without a response before any action; judge Retry by navigations, never by server counts.

### Failures and release

`ProcessFailed` with the browser process, the main frame's render process or a frame's render process gone is a browser failure: fatal, with no restart. An unresponsive renderer and the auxiliary processes the engine restarts itself (GPU, utility, sandbox helper) are recorded in the attachment's events, not fatal. Before close, any `BrowserProcessExited` is fatal. During close, a confirmed normal exit is the expected end. A failed exit, or one whose kind cannot be read because `get_BrowserProcessExitKind` failed, is fatal and reaches the core before teardown proceeds; the exit itself still lets release proceed. Close removes the `ProcessFailed` handler, so during close the exit is the only report of a browser crash. One browser-process failure is reported once, whether `ProcessFailed` or the exit brings it first. A renderer failure is always its own report. Close stops the page, settles waiting and reading requests (readers as described above), removes every event handler, closes the controller and releases the web view while the shell is still valid, then waits: for a creation callback still due (a late environment is released, a late controller is closed, neither is attached), for every completion handler still owed, for every body reader's worker to return, for the browser process's exit, and for the engine's final release of every response stream it still holds. The controller is closed first, so the engine can drop those streams. A stream is counted from its creation, and its final release is the single decrement, including the host's own release when creating the response failed. Whether the real engine drops its last reference promptly after the controller closes still has to be validated on Windows. A completion handler WebView2 releases without invoking it, as `Close` does to a pending `GetCookies`, settles through that final release, and an invocation and a release never both settle one operation. One message-loop turn after the last of these, the exit handler is removed, the environment released, the loader's use dropped, the profile's removal scheduled, and the attachment reports released; the core destroys the shell after that. Synchronous completion inside a creation call takes the same path, because routing exists before the call; the installed Runtime completes asynchronously.

The controller follows the shell's copied bounds and visibility and is told when the shell moves and when it gains focus. Diagnostics report the Runtime version, the attachment's stage, its native requests, its body readers, the response streams the engine still holds, and the creation callbacks, completions and process exit still owed.
